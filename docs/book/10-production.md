# 10장. 게임을 전달하는 제작 도구

## 필요한 도구를 작업 흐름에서 찾는다

새 게임을 만들 때 거대한 에디터부터 만드는 것은 쉽지만 비용이 크다. 이 프로젝트에서는 실제 반복 작업에서 도구를 정했다. 창 없이 역사를 진행하기, 시드를 비교하기, 저장 파일을 검사하기, 콘텐츠 오류를 찾기, 그림을 같은 방식으로 촬영하기, 원고를 한 권으로 묶기, 타깃 OS용 배포 파일을 만들기다.

| --- | --- | --- |
| campaign / simulate | 시드·주수·제목 | 캠페인 저장과 JSON 보고서 |
| balance | 시드 수·주수 | 여러 세계의 판세와 마지막 행동 |

## 플랫폼에 맞춰 저장한다

소스 실행은 프로젝트의 saves 폴더를 쓴다. 편집과 테스트에 편리하며 파일 위치가 눈에 보인다. 배포 앱은 Windows의 LOCALAPPDATA 또는 Mac의 Application Support 아래에 저장한다. 앱 설치 폴더가 쓰기 가능하다고 가정하지 않는다.

테스트와 임시 실행에는 CHAOS_KINGDOM_HOME 환경 변수로 별도 위치를 지정한다. 코드와 배포 앱은 같은 저장 함수를 쓰고 위치 선택만 달라진다. 사용자 저장을 테스트가 덮어쓰지 않는 것이 중요하다.

## Windows와 Mac 빌드를 구분한다

PyInstaller는 현재 OS의 실행 파일과 라이브러리를 묶는다. Mac에서 실행한 빌드로 Windows exe가 만들어지지 않는다. 따라서 GitHub Actions에 Windows·Mac 매트릭스를 두고, 각 OS에서 같은 테스트와 빌드 스크립트를 실행하도록 설정했다.

로컬에서 Mac 빌드를 만들더라도 Windows 실행을 검증했다고 말할 수 없다. CI 설정이 있다는 사실과 실제 CI가 실행되었다는 사실도 다르다. 확인된 결과는 검증 기록에서 구분한다. 배포 서명과 공증, 설치 프로그램과 업데이트 정책은 별도의 출시 작업이다.

Mac 앱 묶음은 프레임워크의 심볼릭 링크와 실행 권한도 보존해야 한다. 따라서 배포 도구는 Mac의 `ditto`로 앱을 압축한 뒤 원고와 안내를 추가한다. 압축 파일을 다른 폴더에 풀고 그 실행기로 콘텐츠 검사와 화면 렌더를 수행해, 빌드 폴더에서만 작동하는 앱을 전달하지 않도록 확인한다.

## 원고 편찬기의 작은 계약

편찬기는 파일 이름 순서대로 장을 읽고 제목·문단·목록·표·코드·그림을 HTML로 변환한다. 목차는 각 장의 시작으로 이동한다. 책 그림은 HTML 안에 데이터로 넣어 한 파일로 전달할 수 있게 한다. 원격 리소스를 내려받지 않고 프로젝트 안의 이미지로 제한한다.

이 도구는 Markdown의 모든 확장을 지원하는 범용 변환기가 아니다. 원고에서 실제 사용하는 문법만 지원한다. 지원하지 않는 문법을 새로 쓰면 변환 규칙과 검증도 바꾼다. 출판 교정의 요구가 커지면 전문 조판 도구로 옮길 수 있도록 원본 원고는 유지한다.

## 도구도 실패를 알려야 한다

내용 검사기는 수도가 존재하는지, 이름 조합이 200명을 만들 수 있는지, 이름이 겹치지 않는지 확인한다. 캠페인 도구는 잘못된 주수와 깨진 저장을 종료 코드로 알린다. 빌드 스크립트는 PyInstaller의 종료 코드를 돌려준다.

개발 도구의 실패를 성공 메시지로 덮으면 이후의 원고와 검증도 오염된다. 파일이 생성되었다는 것과 그 파일이 올바르다는 것을 구분하는 태도는 게임과 책 양쪽에 적용된다.
