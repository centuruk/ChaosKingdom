# 13장. 개발 에이전트 구성과 작업 계약

## AGENTS.md 밖에서 읽고 사용한 지침

사용자는 프로젝트의 `AGENTS.md` 외에 다른 에이전트나 스킬을 사용한다면 그 내용도 원고에 기록해 달라고 요청했다. 이에 따라 `docs/production/workflow-tools.json`을 추가했다. 이 명세는 실제 개발 주체, 지침의 원문 경로와 SHA-256, 적용 목적, 실행한 도구, 연결된 산출물을 구분한다. `tools/agent_catalog.py`가 역할 명세와 함께 필수 항목 및 프로젝트 산출물 존재를 검사한다. 다른 PC에 개발자의 스킬 설치 경로가 없더라도 게임은 실행된다. 이 경로는 제작 출처이며 게임 의존성이 아니다.

| 지침 또는 도구 | 이번 작업의 상태 | 실제 적용과 산출물 |
| --- | --- | --- |
| 프로젝트 `AGENTS.md` | 적용 | 200장수·20성·30거점·1,000명 상한, 시뮬레이션/UI 분리, 저장 호환, 실제 검증과 원고 갱신 |
| `imagegen` 스킬 | 적용·내장 이미지 도구 실행 | 투명 아이소 성벽·성문·탑·다리 시트와 병종 부대 시트, 프롬프트·원본·출처 명세 |
| `superdesign:superdesign` 스킬 | 지침 참고 | 독립 이미지 자산에는 호스트 내장 생성기를 우선 사용한다는 경로 선택. Superdesign CLI·캔버스·업로드·모델 비교는 실행하지 않음 |
| Codex 주 개발 에이전트 | 실제 1개 | 설계·코드·미술 도구 호출·검증·집필·통합 |
| 보조 에이전트 | 별도 실행 없음 | 일곱 역할 계약을 여러 에이전트의 병렬 실행으로 기록하지 않음 |

실제로 읽은 스킬 원문은 다음과 같다.

- [imagegen / SKILL.md](/Users/centuruk/.codex/skills/.system/imagegen/SKILL.md)
- [superdesign / SKILL.md](/Users/centuruk/.codex/plugins/cache/openai-curated-remote/superdesign/0.6.0/skills/superdesign/SKILL.md)
- [superdesign / ASSET_GENERATION.md](/Users/centuruk/.codex/plugins/cache/openai-curated-remote/superdesign/0.6.0/skills/superdesign/references/ASSET_GENERATION.md)

`imagegen`은 제작 절차를 안내하는 스킬이고 `image_gen.imagegen`은 호출한 도구다. 스킬 자체가 새로운 작성자나 게임 AI가 되는 것은 아니다. 이번에는 내장 GPT Image Generator를 사용했으며 별도 Image API나 API 키, Superdesign CLI를 실행하지 않았다. 생성된 원본은 그대로 보존하고 PyGame이 시트의 각 셀을 읽어 화면 크기에 맞춰 표시한다. 두 방향의 성벽이 같은 방향으로 생성된 경우에는 주소 명세에 런타임 좌우 반전을 기록했다.

브라우저·네이티브 조작에는 `unified-computer-use` 플러그인의 `mcp__cua_repl.js` 도구를 사용했다. 이 플러그인의 별도 SKILL.md를 읽거나 보조 에이전트를 실행한 것은 아니다. 원고 브라우저 검증은 통과했고, 새 Mac 게임 창은 화면 잠금 때문에 실행을 확인하지 못했다. 이런 도구 실행 상태도 명세와 실제 검증 기록에 남긴다.

2026년 10월 1일 후속 실행에서는 같은 도구로 `dist/ChaosKingdom.app`을 실행하고 창을 앞으로 가져온 뒤, ‘저장한 이야기’를 마우스로 눌렀다. 메뉴의 `v0.3.0-beta.1` 표시와 아델 발렌의 기존 29주 캠페인 지도 화면을 실제 창에서 확인했다. 사용자가 바로 이어서 플레이하도록 지도 화면을 열어 두었다. 이번 확인은 실행·저장 불러오기·지도 표시에 한정되며, 새 버전의 네이티브 전투와 편집기 조작 검증으로 확대해서 기록하지 않는다. 별도 에이전트나 추가 스킬은 사용하지 않았다.

파일 작업은 `functions.exec`의 `exec_command`와 `apply_patch`, 규칙 검증은 pytest·지도 검사·장기 실행 스크립트, 그림 확인은 실제 PyGame 렌더를 사용한다. 네이티브 창 입력을 확인하는 도구와 headless 화면 촬영은 서로 다른 검증으로 기록한다. 앞으로 다른 스킬 또는 보조 에이전트를 실제로 쓰면 같은 명세와 이 장에 추가하고, 담당 파일·실행 ID·산출물·검토 결과를 남긴다.

이 장의 기록 범위는 확인 가능한 현재 작업이다. 과거 대화에서 읽었는지 확인할 수 없는 스킬을 추정해 소급 등록하지 않는다.

## 실제 실행 구성부터 기록한다

이 개발에서 소스와 원고를 작성한 주체는 Codex 주 개발 에이전트 하나다. 설계·시뮬레이션·전술·아트·검증·집필을 같은 에이전트가 담당했다. GPT Image Generator는 호출한 이미지 생성 도구이고 pytest와 제작 스크립트는 실행 프로그램이다. 역할 일곱 개를 정의했다는 사실을 독립 에이전트 일곱 개가 실행됐다는 기록으로 바꾸지 않는다.

현재 실행과 책임의 연결은 다음과 같다.

```text
사용자 요구·추가 설명
  → Codex 주 개발 에이전트 1개
      요구 해석 / 설계 / 코드·원고 수정 / 결과 통합
      ├─ GPT Image Generator → PNG 원본·프롬프트·출처
      ├─ Python·PyGame 실행 → 시뮬레이션·게임·편집기
      ├─ pytest·audit·검사 도구 → 성공·실패 근거
      └─ 파일·브라우저·네이티브 UI 확인 → 편찬·실행 결과
  → 게임·도구·원고·검증 기록·배포 후보
```

그림 생성 도구가 게임의 규칙을 결정하거나 검증 스크립트가 책을 집필하는 구조가 아니다. 해석과 통합 책임은 주 개발 에이전트에 남는다. 또한 단일 작성자가 자기 작업을 검증한 결과이며 독립 검토자나 외부 플레이테스터의 평가를 받은 것으로 쓰지 않는다.

## 역할 구성은 파일로 재현한다

`docs/production/agents.json`에는 실행 상태와 역할 계약을 남겼다. 핵심 상태의 실제 값은 다음과 같다.

```json
{
  "execution": "single_controller",
  "actual_development_agents": 1,
  "specialists_status": "role_contracts_not_spawned",
  "game_runtime": "offline utility and tactical AI; no LLM calls",
  "art_provider": "Codex built-in GPT Image Generator"
}
```

`roles`의 각 항목은 `id`, `name`, `instructions`, `inputs`, `outputs`, `acceptance`를 가진다. 역할 ID는 총괄 `controller`, 설계 `design`, 세계 시뮬레이션 `simulation`, 전술·도구 `tactics_tools`, 미술 `art`, 검증 `qa`, 집필 `author`다. `tools/agent_catalog.py`는 역할 수·필수 항목·입력 파일 존재를 확인한다. 이 스크립트는 에이전트를 실행하거나 모델 API를 호출하지 않는다.

역할을 나눈 이유는 작업을 놓치지 않기 위해서다. 그림을 만들면 배치 주소와 실제 화면 검증이 필요하고, 행동을 만들면 시뮬레이션뿐 아니라 저장·UI·원고까지 연결해야 한다. 역할 계약은 한 에이전트가 책임을 바꿔 가며 작업할 때도 유용하다.

| 역할 ID | 주요 입력 | 책임과 작업 파일 | 통합할 때 받을 증거 |
| --- | --- | --- | --- |
| controller | AGENTS.md·README·검증 기록 | 공통 계약·작업 순서·통합 | 구현·원고·배포의 일치와 남은 확인 항목 |
| design | 1장·beta-audit.json | 규칙의 목적·비교 조건 | 같은 편성·시드에서의 전후 관측 |
| simulation | models.py·ai.py·engine.py | 세계 상태·주간 행동·경제·관계 | 200명·50지역·병력 상한·저장 재현 |
| tactics_tools | battlefields.py·test_beta.py | battle.py·editor.py와 공유 스키마 | 통행·시야·연결·시험 전투·이중 결산 거부 |
| art | manifest.json·15장 | PNG·출처·ui/assets.py의 주소 | 실제 생성 원본·프롬프트·적용 화면 |
| qa | test_beta.py·beta_audit.py | 검사·재현·플랫폼 확인 | 종료 코드·원본 로그·재현 가능한 결함 |
| author | 원고 목차·검증 기록 | 관련 장·그림·book.html | 현재 구현과 역사적 실험·후속 제안의 구분 |

이 표의 파일 분담은 작업 계약이다. 현재 여러 작성자가 파일을 동시에 소유했다는 뜻은 아니다. 별도 에이전트를 실제로 배치하는 후속 개발에서는 편집 가능한 파일과 공유 인터페이스를 더 엄격하게 지정해야 한다.

## 실제 작업은 어떻게 이어졌는가

세계 모델을 먼저 만들고 화면 없이 24주를 진행했다. 모델과 규칙이 돌아가는 것을 확인한 뒤 화면과 저장을 붙였다. 베타 확장에서는 같은 전장 스키마를 전투·에디터·제보 도구가 읽게 했다. 이미지 생성 뒤에는 원본을 보존하고 자산 주소를 맞춘 다음 실제 화면을 다시 그렸다. 검증과 집필은 이 결과를 받아 소스와 문장을 대조했다.

실패도 이 연결 안에서 다뤘다. 초상 시트는 요청한 열 수를 항상 지키지 않았다. 실제 열 경계를 읽어 주소를 보정했다. 전술 판단을 강화했을 때는 우회 명령을 자동 판단이 너무 빨리 덮어썼다. 명시한 명령 뒤 8초 동안 판단을 미루고 회귀 검사를 돌렸다. Mac 앱에서는 편집기 시험 전장의 지형 제목이 임시 세계를 읽던 표시 오류와 진행 중 부대 숫자 겹침을 발견했다.

이번 자연 지형 작업에서도 요구 해석이 바뀌었다. 사용자의 “스타1처럼 자연스러운 산·바닥·강”을 높이차로 확장하지 않고, “단차가 있으라는 말은 아니다”라는 설명에 맞춰 평면 재질·연결·경계의 문제로 정의했다. 아트 역할은 새 재질 시트를 만들고, 전술·도구 역할은 덩어리 지형 생성과 표시 합성을, 검증 역할은 편집·복원·통행·전투를, 집필 역할은 선택 이유와 객체 책임을 기록했다. 이것은 하나의 에이전트가 역할을 이어 수행한 실제 사례다.

## 작은 작업을 맡길 때 쓰는 계약

후속 제작에서도 다음과 같이 요청을 구체화할 수 있다. 아래는 지형 표시 작업에 맞춘 계약 예이며 별도 에이전트 실행 로그가 아니다.

```text
목표: 숲·바위·수변이 이어지는 평면 전장 표시를 만든다.
읽을 파일: AGENTS.md, battlefields.py, battle.py, editor.py,
           assets.py, 관련 테스트, 이미지 출처 명세.
변경 범위: battlefield_view.py와 필요한 표시 연결.
고정 계약: 전장 schema 1, 32×20 배열, 높이 필드 없음,
           물·성벽 통행 불가, 판정은 Battlefield가 담당.
산출물: 적용 코드, 실제 전장 화면, 테스트 결과,
        표시와 이동 판정이 달라질 수 있는 경계 설명.
실패 조건: 편집 뒤 옛 그림이 남음, 화면을 그려 세계가 바뀜,
           저장된 전투의 전장이 새 기본 지도로 바뀜.
```

“자연스럽게 만들어라”만 주면 산출물을 통합할 때 판단 기준이 부족하다. 반대로 색과 함수 구현까지 모두 고정하면 작업자가 더 나은 방법을 선택하기 어렵다. 고정해야 할 것은 공유 데이터와 행동 계약이며, 구현 방법은 그 안에서 선택할 수 있게 한다.

## 문맥·파일·검증을 함께 전달한다

필수 문맥은 사용자 요구, `AGENTS.md`, 관련 코드와 테스트, 현재 원고, 최신 검증 기록이다. 대화의 기억만으로 병력 상한과 저장 형식을 전달하지 않는다. 결과는 “완료했다”라는 한 문장보다 변경 파일, 선택 이유, 실제 실행, 실패와 남은 항목을 포함해야 한다.

작업 간 의존 순서도 관리한다. 전장 스키마를 정하기 전에 편집기와 전투가 서로 다른 배열을 만들면 통합 비용이 커진다. 이미지 시트의 실제 행·열을 확인하기 전에 초상 주소를 고정하면 얼굴을 잘못 잘라 읽는다. 원고는 구현과 검증을 받은 뒤 현재 결과를 설명해야 한다. 독립된 파일 읽기나 검사는 도구 호출을 함께 실행할 수 있지만, 그것이 독립 에이전트 실행을 의미하지는 않는다.

검토는 작성자의 설명을 반복하는 과정이 아니다. 다른 시드, 잘못된 입력, 저장 후 이어 실행, 지형 편집 후 되돌리기로 주장에 반례를 찾는다. 현재 지형 검사도 “그림이 바뀌었다”뿐 아니라 편집 즉시 갱신, 되돌리기 뒤 동일한 그림, 격자 표시가 세계와 지형을 바꾸지 않음을 확인한다. 모든 자동 검사와 50개 지역 전투가 끝나야 다시 배포 후보를 만든다.

## 실제로 여러 에이전트를 쓰게 된다면

후속 확장안은 총괄이 책임을 유지하고 작은 전문 작업을 보조 에이전트에 맡기는 방식이다. 공통 모델과 저장 스키마의 변경은 먼저 통합 계약을 정하고, 전술 작성자가 battle.py를 수정하는 동안 집필 작성자는 그 파일을 수정하지 않고 결과를 받아 원고를 갱신한다. 공유 폴더의 동시 수정은 별도의 충돌 관리가 필요하다.

OpenAI 공식 문서는 총괄이 전문 에이전트를 도구로 호출하는 방식과 다른 에이전트에 제어를 넘기는 방식을 구분한다. 이것은 향후 설계 참고이며 현재 게임에 Agents SDK를 설치하거나 실행한 사실은 아니다. [OpenAI의 에이전트 오케스트레이션 문서](https://developers.openai.com/api/docs/guides/agents/orchestration)

추가 실행 기록에는 실제 작업 ID·담당 범위·산출물·검토 결과를 남겨야 한다. 역할 이름만으로 독립 검토가 이루어졌다고 쓰지 않는다. 이 책에서 재현하려는 것은 조직도의 인상이 아니라 요구에서 코드·그림·검증·문서로 이어지는 책임의 연결이다.


알파 제보 후속 수정에도 같은 주 개발 에이전트 1개가 참여했다. `functions.exec`로 픽셀 형식·원본 해시·회귀 검사·Mac 빌드를 조사하고, `unified-computer-use`의 `mcp__cua_repl.js`로 수정 앱의 메뉴, 연습 전투와 성곽·강 편집기를 마우스로 열어 육안 확인했다. Cocoa 렌더 검사와 관측 결과는 `docs/evidence/alpha-compositing-qa.json`에 연결했다. 이 작업의 별도 에이전트 실행과 추가 스킬 적용은 없으며 GPT 이미지 원본도 유지했다.


공개 저장소 작업에서는 `/usr/bin/git`과 `/opt/homebrew/bin/gh`를 `functions.exec / exec_command`로 실행했다. `git`은 로컬 main 초기화·스테이징·커밋을, GitHub CLI는 기존 인증 확인·Public 저장소 생성·최초 푸시와 원격 메타데이터 조회를 담당했다. 추가 에이전트나 스킬을 적용한 작업은 아니다. 실행 명세에 도구 이름·명령·목적·출처를 추가했고, [공개 저장소](https://github.com/centuruk/ChaosKingdom)와 `docs/evidence/github-publication.json`을 산출물로 연결했다. GitHub 커넥터를 실행했다고 기록하지 않는다.
